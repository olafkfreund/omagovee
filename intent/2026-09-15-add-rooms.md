# Intent: Add new rooms and move lights between them reliably

## Problem

Lights can be moved between rooms that already exist, from the CLI
(`rooms assign`) and the panel (drag onto a room heading, or the room chips).
A new room cannot be created from the panel at all: the chips and drop
targets only offer rooms that already exist, and an empty room is deleted by
the CLI and hidden by the panel. From the CLI a room only appears as a side
effect of `rooms assign <new-name> <device>`.

Review of the room code also found defects that make moving lights
unreliable, two of them reproduced on 2026-09-15 against a scratch config:

1. `rooms <room> <device>...` adds the device without removing it from its
   old room, so one light ends up in two rooms (reproduced: `lvrt1` in both
   `hall` and `office`). A `room:` command then fires it twice and the panel
   draws it twice. It also stores the typed argument unresolved, so a
   friendly label is saved instead of the device name and matches nothing.
   The README recommends this form.
2. `rooms rename <old> <new>` onto an existing room silently replaces that
   room's members, losing them (reproduced).
3. Room names `none`, `other` and `all` are accepted but collide with meanings
   elsewhere: `none` cannot be assigned to, and dropping onto a real room
   named `other` unassigns the device instead.
4. Device lookup matches any substring and takes the first hit, so
   `rooms assign office lvrt1` can move `lvrt10`.
5. Only the room heading accepts a drop; dropping on the room's device list
   does nothing.

## Proposed outcome

- From the panel, a user can create a new room by giving it a name while
  placing a light in it, and can then drag other lights into it.
- From the CLI, every way of putting a light in a room leaves it in exactly
  one room, and names the device the user meant.
- Renaming a room never loses lights.
- Reserved room names are refused with a clear message.
- Dropping a light anywhere on a room moves it there.
- A self-check covers the "one light, one room" rule for every CLI path.

## Affected users and systems

- `bin/omarchy-govee` — room commands and device lookup.
- `plugin/Govee.qml` — Omarchy bar widget panel.
- `test_omagovee.py`, `README.md`.
- Existing `~/.config/omagovee/rooms.json` files on the user's machine; may
  already contain a device in two rooms from defect 1.
- Scenes in `scenes.json` that reference `room:<name>`.
- The one user of the tool (the author). No hosts or services beyond the
  desktop running the widget.

## Constraints

- Python stdlib only; no new dependencies in the CLI or the plugin.
- The panel keeps no room logic of its own: every change shells out to
  `omarchy-govee`, so CLI and panel cannot disagree.
- Existing `rooms.json`, `labels.json` and `scenes.json` must keep working
  without manual migration.
- Existing commands (`rooms assign`, `rooms rename`, `room:` targets) keep
  their meaning for valid input.
- The drag gesture fixed in 2128726 (`preventStealing`, handle column) must
  not regress.

## Open questions

1. Should empty rooms be allowed to exist (create a room first, fill it
   later), or is "a room is created together with its first light" enough?
   The second needs no data-model change; the first means empty rooms
   persist and are drawn.
2. `rooms <room> <device>...` today *replaces* the room's member list. Should
   it become an alias for `assign` (adds and moves), or keep "set exactly
   these members" while also removing them from other rooms?
3. Rename onto an existing room: refuse, or merge the two rooms?
4. Should an existing `rooms.json` with a device in two rooms be repaired
   automatically on load, or left for the user to fix?
